Matrix federation megolm rotation bug

Andrew Miller (@amiller / @socrates1024:matrix.org) · first written 2026-05-10 · draft

TL;DR. A federation hiccup that drops an m.room_key to-device EDU leaves a Matrix bot sending forever to a room whose recipients have no key. matrix-js-sdk doesn't retry, matrix-rust-sdk doesn't auto-rotate. The repro harness reproduces this exactly; a periodic forceDiscardSession patch fires but does not actually unwedge the room.

Origin

Came out of an admin-room flood incident on the Account-Link Matrix homeserver on 2026-05-09. Full retro: docs/incidents/2026-05-09-announce-flood.md in Account-Link/shape-rotator-matrix. The flood (a separate application-logic bug) was loud because the bot's device had been rotated by a self-heal earlier in the day, so peers couldn't decrypt anything it sent. That recovery from the rotation never happened on its own — the same pattern we'd seen once before with claw-teedah-2 versus Router during a matrix.org federation queue backoff. This page is the breakdown of that sub-bug, separated from the day-of incident.

The bug mechanism

Sender side (matrix-js-sdk, Router):

  1. Bot creates a fresh outbound megolm session for an encrypted room.
  2. Bot olm-wraps an m.room_key (carrying that megolm session's ratchet seed) per recipient device, ships them as m.direct_to_device EDUs in the next federation PUT /send/{txn}.
  3. Federation peer returns 200. To matrix-js-sdk this means "delivered".
  4. Bot caches the outbound session and reuses it for every subsequent m.room.encrypted in that room.

What can go wrong: the peer accepts the transaction (200) but the to-device EDU never makes it into the recipient HS's queue — dropped by an intermediary, mangled by federation backoff, lost during a queue-purge window. Once that 200 is observed, matrix-js-sdk has no retry path. The session stays cached and broken.

Receiver side (matrix-rust-sdk, peer): no megolm key arrives, every m.room.encrypted from this sender fails with megolm — no session key. matrix-rust-sdk does have a recovery flow (request keys from sender, accept reshare), but it's gated on cross-signing trust between the two devices. Bots running fresh re-mints don't have cross-signing set up, so that recovery silently no-ops.

Net result: the bot sends to that room indefinitely; the peer sees a wall of undecryptable events; nothing on either side will fix it without an external nudge.

Repro harness

Lives at tests/federation-repro/ in jameslbarnes/teleport-router#31 (currently draft). Architecture:

peer query hs-a:8448 ──TLS──▶ hs-a (nginx) ──HTTP──▶ hs-a-core (continuwuity :6167)
peer query hs-b:8448 ──TLS──▶ hs-b (nginx) ──HTTP──▶ hs-b-core (continuwuity :6167)

Two continuwuity homeservers, shared self-signed CA, federation between them over TLS. The hs-b proxy is an HTTP MITM that can be flipped between pass-through and "drop all m.direct_to_device EDUs" via an env var.

Drivers:

  • repro/bot.ts — uses Router's actual MatrixPlatform (matrix-js-sdk + rust-crypto), CLI over stdin: create-room, invite, send, rotate, exit.
  • repro/user.py — matrix-nio user on hs-b, prints {"event":"decrypt_ok","body":...} or "decrypt_fail" per inbound encrypted event.
  • scripts/run-bug.sh — orchestrates the full scenario below.

Scenario, from scripts/run-bug.sh

  1. baseline: bot sends baseline-ping, user decrypts ok.
  2. arm MITM (drop m.direct_to_device).
  3. forceDiscardSession on bot, send stuck-1: fresh outbound megolm session, its m.room_key EDU is dropped by the MITM, the m.room.encrypted still reaches the user.
  4. send stuck-2 reusing the same broken session.
  5. disarm MITM.
  6. send post-restore reusing the broken session — federation is healthy again but matrix-rust-sdk has nothing to retry, since matrix-js-sdk thinks the key was delivered.
  7. wait past the periodic-rotation interval (compressed to 8s for the test).
  8. send after-rotation.

With the fix

The patch (installMegolmAutoRotation in server/src/platform/matrix.ts) installs two triggers:

  • a sync-recovery hook on ClientEvent.Sync that fires when the state transitions back into SYNCING from a non-syncing state;
  • a periodic setInterval (default 4h, compressed for tests).

Both call rotateAllOutboundMegolmSessions, which loops every encrypted room and calls crypto.forceDiscardSession(roomId).

The patch does fire as designed — bot.out shows both Router's log lines and matrix-js-sdk's internal log:

[Matrix] megolm auto-rotation installed (every 8s + on sync recovery)
...
[!9zEhL2yftkgQP9C3Z0u1kMV_BscGhxOP9lXji8aSq_Y encryption] Discarded existing group session
[Matrix] discarded 15 outbound megolm session(s)
[!9zEhL2yftkgQP9C3Z0u1kMV_BscGhxOP9lXji8aSq_Y encryption] Discarded existing group session
[Matrix] discarded 15 outbound megolm session(s)

But the user still can't decrypt the after-rotation message. forceDiscardSession evicts the cached outbound megolm session, so the next send creates a fresh one — and presumably re-distributes a fresh m.room_key. That should work, but in the harness it doesn't.

Conclusion: the patch as written needs more work before it can be merged. PR #31 stays draft.

Hypotheses for the next iteration

  • Olm session refresh. Maybe the underlying olm sessions with the recipient devices are themselves wedged from the MITM window. A /keys/claim for users in the room should force fresh one-time-keys and new olm sessions, after which a re-share can ride a channel that actually works. Worth trying before the discard.
  • Active reshare. Look for a public path equivalent to matrix-rust-sdk's shareGroupSession — push the session keys out without waiting for the next encrypted message to trigger key distribution. A discard-then-share-explicitly may behave differently from discard-then-rely-on-next-send.
  • Device-list re-validation. If matrix-js-sdk's cached device list for the room is also stale after a federation hiccup, the reshare might target the wrong device set. Force a device-list reload before rotating.

None of these are confirmed yet — they're the next things to try.

Status

PR #31 stays draft. Production (shape-rotator-matrix CVM) currently runs without the patch; manual device rotation has been the workaround. The harness is reproducible locally with docker compose + bash scripts/run-bug.sh.
