3. What lives where on the wire

4. Trust tiers and key-request gating

Bots typically sit in untrusted. matrix-rust-sdk's default key-share policy refuses to forward m.room_keys to untrusted devices, so m.room_key_request from a fresh bot device silently no-ops.

5. Federation transaction lifecycle

Sender retries until 200 OK. 200 OK means "transaction accepted for processing" — not "PDUs auth-passed", and definitely not "EDUs delivered to client".

7. Continuwuity quick-reference

  • RocksDB schema 18 at time of writing (spring 2026). Migrations forward-only.
  • Default room_version: v12. shape-rotator-matrix pins lobbies to v11 to avoid federated-join state desync.
  • No direct_tls in the published image. Run behind nginx (or similar) for the 8448-equivalent endpoint.
  • CONDUWUIT_REGISTRATION_TOKEN seeds DB at first boot only. Rotate via admin command or wipe data volume.
  • No purge_history. No per-event admin delete. Only ban-room for mass-cleanup, which is functionally a room delete.
  • Admin tokens bypass rc_message per-user rate limits. Any send-loop on an admin bot becomes a flood. Don't /send as admin if a non-admin would do.
  • /redact caps ~3.5/s in our measurements even with admin token. Cleaning a 600K-event self-DOS this way takes hours.
  • Restart discipline. 6+ restarts in 5h can stick matrix.org's federation queue for hours; recovery is "wait", not "more restarts".
  • Bot self-heal: bots check /account/whoami at boot; remint via /login with persisted password; reuse device_id to keep crypto store intact.
