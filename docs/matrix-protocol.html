Matrix protocol & continuwuity — operator's deep dive

Andrew Miller (@amiller / @socrates1024:matrix.org) · first written 2026-05-10 · draft

What this is. A self-contained reference for the parts of the Matrix protocol you actually need to understand to run a homeserver and bots on it. Federated event-sourced rooms, Olm + Megolm, to-device delivery, and the operational footguns of continuwuity specifically. The megolm rotation bug is the motivating case study at the end — every layer it touches is documented above it.

1. Rooms as federated event-sourced state machines

A Matrix room is a directed acyclic graph of events. Every event is signed by the sending server, references its predecessors by hash, and is replicated to every server that has a member in that room. There is no master copy of a room; conflicts between divergent histories are resolved deterministically (state resolution v2, below). Federation is therefore an active-active multi-master replication system, not a master/replica one.

1.1 Events: PDUs and EDUs

Two transport categories, with very different semantics:

KindPersisted?Replicated to whom?Examples
PDU (Persistent Data Unit) Yes — part of the room DAG forever All servers with a member in the room m.room.message, m.room.member, m.room.encrypted, m.room.create, m.room.power_levels, m.room.encryption
EDU (Ephemeral Data Unit) No — best-effort, fire-and-forget One target server (or many, depending on EDU type) m.typing, m.receipt, m.presence, m.direct_to_device

The federation spec calls EDUs "ephemeral" and is explicit that "they are not persisted and are not part of the history of a room, nor does the receiving homeserver have to reply to them" (server-server-api §EDUs). This is load-bearing for the to-device-delivery story below: the m.room_key messages that distribute Megolm session keys ride inside m.direct_to_device EDUs, which means key delivery is not, at the protocol level, durable.

1.2 Room events vs state events

Every PDU has a type (m.room.message, m.room.encrypted, m.room.member, ...) and optionally a state_key. Events with a state_key are state events: they update the room's state map keyed on (type, state_key). Events without one are timeline events: they're sequenced into the timeline but don't change room state. So m.room.member with state_key="@bob:example.org" sets Bob's membership; m.room.message with no state_key just adds to the chat log.

The auth rules are state-event-aware: whether you can send an event depends on the current m.room.power_levels state, your m.room.member state, and the room's m.room.create event. Each event explicitly references the state events it relies on for authorization, via auth_events. This is what makes state resolution deterministic across forks: every server, given the same DAG, can recompute the same authorized state without coordination.

1.3 State resolution v2 (briefly)

When two servers' views of the room state diverge (say a partition lets both sides admit a new member), state resolution v2 picks a winner per state key. The algorithm is in rooms/v2 §State resolution; the short version is: take the intersection of unconflicted state, then for conflicted state keys re-run auth checks in a deterministic topological order seeded by power-level events. Room versions can tweak the algorithm — v12 notably changed the seed from the unconflicted state map to an empty map (rooms/v12).

For operational debugging this rarely matters directly, but it matters indirectly: a bot whose recent messages are getting 403 Event is not authorized on the receiving server is usually the victim of either a stale federation cache of state or a state-resolution divergence. The fix is almost always "rejoin the room" — which forces the bot's server to fetch fresh state via send_join.

1.4 Room versions, and why we pin to v11

Room versions are immutable per room: a room is created at one version and stays there. Newer versions tighten auth rules, change event hashing, or restructure event content. The relevant ones for us:

  • v11 — clarifies redaction rules. The creator property is removed from m.room.create (clients use sender instead); m.room.redaction.redacts moves from top-level into content; origin / membership / prev_state are no longer redaction-protected (rooms/v11).
  • v12 — much bigger change. Room IDs are now a hash of the m.room.create event rather than including a domain. Introduces room creators as a formal concept (the create event's sender plus any additional_creators); these identities have infinite power level and cannot be demoted. m.room.create is no longer included in any other event's auth_events, and state resolution starts from an empty state map instead of the unconflicted one (rooms/v12).

Continuwuity's default room_version at the time of writing is v12. shape-rotator-matrix pins lobbies to v11 in approver.py:_create_lobby_room_raw. Reason: rooms created at v12 produced cases where a federated user joining the room left the bot's local membership state desynced — 404 on /rooms/{id}/state/m.room.member/{bot}, then 403 Event is not authorized on subsequent sends, then M_NOT_FOUND on /join. Pinning to v11 keeps the room firmly local-authoritative and uses the well-trodden federation path. Whether the underlying issue is in continuwuity's v12 implementation or in matrix.org's federated handling of v12 we haven't isolated; the pin is a stopgap, not a diagnosis.

2. End-to-end encryption

Matrix E2EE uses two cryptographic primitives layered on top of each other. You need both. The split exists because they solve different problems:

OlmMegolm
Algorithm IDm.olm.v1.curve25519-aes-sha2m.megolm.v1.aes-sha2
Topology1:1 between two devices1:N from one sender to many recipients
RatchetDouble Ratchet (Signal-style); forward secrecy + post-compromise security per messageHash ratchet, sender-only; forward secrecy but no post-compromise security within a session
Used forTo-device messages, especially carrying Megolm session keysRoom messages (m.room.encrypted events)
Key sharingEstablished by claiming a one-time keySender ships an m.room_key to each recipient device, Olm-wrapped
RotationContinuous (Diffie-Hellman ratchet on every message exchange)Triggered: time-based, message-count-based, or membership change

You can think of Megolm as "I encrypt the symmetric session under the hash ratchet, and Olm is how I get that session into your device". Olm is expensive (asymmetric crypto per recipient) but produces a strong pairwise channel; Megolm is cheap (symmetric encryption) but its key has to be shipped out-of-band over Olm to every device that should see the room.

2.1 Device identity and keys

Every Matrix client session — every device_id — has its own identity:

  • Ed25519 fingerprint key. Long-term signing key. Identifies the device. Stays the same as long as the device exists.
  • Curve25519 identity key. Long-term key used for ECDH during Olm session establishment.
  • One-time keys (OTKs). Short-lived Curve25519 keys uploaded in batches. Each is consumed by one Olm session establishment, then destroyed.
  • Fallback key. A single Curve25519 key that's used when OTKs are exhausted. Per spec, "the fallback key is not deleted once used, but should be replaced when additional one-time keys are being uploaded" ( client-server-api §One-time and fallback keys). Without a fallback, a sender that arrives after a recipient has burned all OTKs has no way to initiate Olm. With one, the recipient gets a slightly weaker initial session that's quickly upgraded by the ratchet.

These all get uploaded via POST /_matrix/client/v3/keys/upload. The OTK pool is replenished by the client on every /sync: the sync response includes a device_one_time_keys_count map, and clients top up to a target count (50 by default in matrix-rust-sdk).

2.2 Sending an encrypted message: end to end

This is the full path that the bug report below depends on. Suppose @bot:hs-a wants to send "hello" into a room shared with @user:hs-b. The bot has never sent in this room before.

  1. Determine recipients. Bot calls POST /keys/query with {"@user:hs-b": []}. hs-a federates this to hs-b if it doesn't already have a fresh device list cached. Response: each device's signed device keys (Ed25519 + Curve25519 fingerprints) plus algorithm support.
  2. Establish Olm sessions per recipient device. For each device the bot doesn't already have an Olm session with, it calls POST /keys/claim, which claims one OTK per (user, device). hs-a federates this to hs-b, hs-b atomically pops one OTK from each device's pool, returns it. Bot now has enough material to do an Olm triple-DH and derive an initial Olm session.
  3. Create outbound Megolm session. Locally — no network. Generate a fresh 32-byte ratchet seed; that's the session key. Compute session_id. Create a fresh outbound session keyed on the room.
  4. Wrap the Megolm key in Olm, per device. Build an m.room_key payload: 
    {
  "algorithm": "m.megolm.v1.aes-sha2",
  "room_id":   "!abc:hs-a",
  "session_id":  "<b64 ratchet pubkey>",
  "session_key": "<b64 session-export-format key>"
}
    Encrypt this with each recipient device's Olm session, producing one Olm-encrypted blob per device. Pack them all into a single PUT /_matrix/client/v3/sendToDevice/m.room.encrypted/{txn} request: 
    {
  "messages": {
    "@user:hs-b": {
      "ABCDEVICE": { "algorithm": "m.olm.v1.curve25519-aes-sha2", ... },
      "XYZDEVICE": { "algorithm": "m.olm.v1.curve25519-aes-sha2", ... }
    }
  }
}
  5. hs-a forwards over federation. hs-a groups by destination server and emits, in the next federation transaction to hs-b, an EDU: 
    {
  "edu_type": "m.direct_to_device",
  "content": {
    "sender":     "@bot:hs-a",
    "type":       "m.room.encrypted",
    "message_id": "<random utf8 ≤ 32 codepoints>",
    "messages": {
      "@user:hs-b": { "ABCDEVICE": { ... }, "XYZDEVICE": { ... } }
    }
  }
}
    Format per server-server-api §Send-to-device messaging: "an EDU that lets servers push send events directly to a specific device on a remote server — for instance, to maintain an Olm E2E encrypted message channel between a local and remote device."
  6. hs-b enqueues per-device. hs-b unpacks, stores per-device, ready to be served on the next /sync for @user:hs-b. The message_id is for idempotence — duplicates are dropped.
  7. Recipient syncs and decrypts. User's client gets the Olm-wrapped m.room.encrypted in the to_device block of /sync, decrypts it, sees the m.room_key, installs an inbound Megolm session keyed on (room_id, sender_curve25519, session_id).
  8. Now the actual message. Bot encrypts "hello" with the Megolm session, advances the ratchet, ships PUT /rooms/{roomId}/send/m.room.encrypted/{txn}. This is a PDU: durable, federated as part of the room DAG. Body looks like: 
    {
  "algorithm":  "m.megolm.v1.aes-sha2",
  "sender_key": "<bot device curve25519>",
  "device_id":  "BOTDEVICE",
  "session_id": "<same session_id as above>",
  "ciphertext": "AwgAEnA...<b64>..."
}
  9. Recipient decrypts. Looks up inbound session by session_id, advances ratchet to the message index, decrypts. Done.

The point of laying it out this way is to make obvious where the bug lives. Step 5 — the m.direct_to_device EDU — is the only step in the chain that's ephemeral. Step 8, the actual message, is durable forever. So a federation hiccup that drops the EDU but lets the PDU through leaves the receiver with a forever-undecryptable message and no protocol-level signal that anything went wrong: hs-a's /send/{txn} got 200 OK, hs-b stored the PDU, the EDU just vanished.

2.3 Megolm session rotation

Megolm sessions don't have post-compromise security: anyone who steals the ratchet state at message N can read all future messages N+1, N+2, ... until the session is rotated. So sessions get rotated.

The trigger parameters are advertised in the room's m.room.encryption state event:

{
  "algorithm": "m.megolm.v1.aes-sha2",
  "rotation_period_ms":   604800000,   // 1 week, recommended default
  "rotation_period_msgs": 100          // recommended default
}

Defaults per client-server-api §m.room.encryption: "How long the session should be used before changing it. 604800000 (a week) is the recommended default" / "How many messages should be sent before changing the session. 100 is the recommended default."

In addition to those two, the spec requires rotation on device list changes: if a recipient device leaves, the existing session must be discarded so they can't decrypt future messages; if a new device joins, the sender must share the (current or new) session to it. matrix-rust-sdk implements both. The "leave" path is the security-critical one; the "join" path is just a key-share, no rotation needed in principle.

What's missing from the spec, and what the bug exploits: there is no required rotation trigger for "the m.room_key I sent on session creation may not have been delivered." The protocol assumes either (a) the key got there, or (b) the recipient will request it via the gossip flow below.

2.4 Key gossip: m.room_key_request and m.forwarded_room_key

If a recipient gets an m.room.encrypted event whose session_id they don't have, they can ask. Per client-server-api §Key requests: "When a device is missing keys to decrypt messages, it can request the keys by sending m.room_key_request to-device messages to other devices with action set to request. If a device wishes to share the keys with that device, it can forward the keys to the first device by sending an encrypted m.forwarded_room_key to-device message."

This is the protocol-level recovery for "I missed an m.room_key". It works in theory. In practice, every implementation gates "willingness to forward" on cross-signing trust between the requesting device and some device that already has the key. The spec actively encourages this: "messages sent from non-cross-signed devices cannot be trusted and SHOULD NOT be displayed to the user. Clients have no assurance that encrypted messages sent from non-cross-signed devices were sent by the user, rather than an impersonator." So matrix-rust-sdk's default is: if the sender of the request isn't cross-signed by someone you trust, don't forward.

For human Matrix users this is fine — you cross-sign your phone from your laptop. For bots it's the central operational headache. A bot that re-mints its login (which shape-rotator-matrix's self-heal does whenever the env token goes stale) gets a new device_id, hence a new device key set, hence is uncross-signed. Until it's manually verified, it can't recover keys via the gossip path. Its peers can't trust messages it sends. The cost of an uncross-signed bot is roughly:

  • It cannot recover keys it missed (no m.forwarded_room_key will be sent to it);
  • Recipients can decrypt its messages but Element renders a "not verified by its owner" warning;
  • Users can't verify the bot via SAS without the bot device first being cross-signed.

Cross-signing footgun. If you write your own bootstrap (bots sometimes need to, since matrix-rust-sdk's bootstrap path requires interactive password handling), do not use padded base64 in keyids. Element's userHasCrossSigningKeys silently rejects the entire master_keys entry from /keys/query if any keyid has trailing =. Symptom: bot uploads keys fine, server stores them fine, federation serves them fine, peers see "Encrypted by a device not verified by its owner" forever. Confirmed via clean A/B in shape-rotator-matrix; documented in MATRIX_ONBOARDING.md.

2.5 Trust tiers

TierWhat it meansWhat it costs
Untrusted (TOFU) Device key seen for the first time, no cross-signing assertion Element shows red shield. Key gossip won't forward to this device by default. Messages decrypt OK if you have the session, but UI flags them.
Cross-signed Some device this user has marked as their own master key has signed this device's identity key Element renders normally. Other clients of the same user will trust this device automatically.
Verified You (the requesting user) have personally verified this device or the user's master key, typically via SAS or QR Strongest tier. Required for some flows. Sticky across logouts.

The transitions: untrusted → cross-signed happens by the user signing their own device with their self-signing key, or by another verified user signing the master key with their user-signing key (in which case it's "transitively trusted" rather than verified). Cross-signed → verified requires explicit user action (SAS / QR / "I trust this device").

3. Federation

3.1 Server discovery

Per server-server-api §Server discovery, resolving server_name to a network endpoint follows a priority order:

  1. If server_name is an IP literal: connect to that IP, port 8448 unless overridden.
  2. If a port is explicit in server_name: DNS-resolve the hostname, connect to the specified port. No further delegation.
  3. Otherwise, fetch https://<hostname>/.well-known/matrix/server. If it returns {"m.server": "delegated:port"}, use that. Cacheable up to 48h.
  4. Otherwise, query SRV record _matrix-fed._tcp.<hostname> (preferred since spec v1.8) or legacy _matrix._tcp.<hostname>.
  5. Otherwise, A/AAAA on the hostname, port 8448.

Operationally relevant point for dstack-hosted homeservers: dstack's gateway only exposes the configured port (in our case 6167), not 8448. So the well-known has to advertise :443 as the federation endpoint (gateway TLS), not 8448. A misconfigured well-known produces "Failed to find any key to satisfy: _FetchKeyRequest" on the peer. federationtester.matrix.org caches failure results — after fixing well-known, expect a delay before re-tests succeed.

3.2 Server signing keys

Each homeserver publishes its current Ed25519 signing keys at GET /_matrix/key/v2/server. Response includes verify_keys (active), old_verify_keys (only valid for verifying historical events), valid_until_ts. Spec caps valid_until_ts at 7 days ahead.

Peers can either fetch this directly or fetch via a perspective / notary: a third server they already trust, which countersigns the target's keys. matrix.org is the most common notary. Notary queries: POST /_matrix/key/v2/query or GET /_matrix/key/v2/query/{serverName}.

3.3 Federation transactions

The actual workhorse of federation:

PUT /_matrix/federation/v1/send/{txnId}
{
  "origin": "hs-a",
  "origin_server_ts": 1715300000000,
  "pdus": [<up to 50 PDUs>],
  "edus": [<up to 100 EDUs>]
}

Limits per server-server-api §Transactions: "max 50 PDUs", "max 100 EDUs". The sender retries with the same txnId until it gets a 200; the receiver dedupes by txnId. Per-PDU errors are reported in the response body but do not fail the transaction: "the server is to use this response even in the event of one or more PDUs failing."

What 200 OK actually means. "We received your transaction and have begun processing." It does not mean "all your PDUs are accepted into the room" — they could still soft-fail on auth checks. It does not mean "your EDUs were delivered to recipients" — EDUs are best-effort and the receiver only commits to processing them, not to durability or delivery to clients. For PDUs, the soft-fail is at least observable on the next state pull. For EDUs, there's no protocol-level visibility at all.

This is the load-bearing fact for the megolm bug: matrix-js-sdk's sendToDevice resolves on a 200 from PUT /_matrix/client/v3/sendToDevice/..., which on a federated recipient means "hs-a accepted it for forwarding," not "hs-b's user has it." There's a federation hop between those two states and no end-to-end ack.

3.4 Per-server federation queue

Each homeserver maintains a per-destination outgoing queue with retry/backoff. When hs-b is unreachable, hs-a accumulates pending PDUs and EDUs for hs-b and retries with exponential-ish backoff. continuwuity has its own implementation here — we have not read the source carefully enough to cite specific intervals — but the observable behavior is:

  • EDUs queued during a backoff window get bunched into a single transaction when the queue drains. Order within a destination is preserved within reasonable bounds.
  • If the queue grows unboundedly during a long outage, EDU losses become possible: the queue may be capacity-bounded and drop oldest, or be purged on restart, or get truncated on too many retries. We have observed m.direct_to_device EDUs being dropped between matrix.org and our continuwuity instance during periods where matrix.org's federation queue for our server was backed up; the bug report linked at the bottom is the careful follow-up.
  • Excessive homeserver restarts make this worse, not better. If you restart conduwuit/continuwuity 6+ times in 5 hours, matrix.org's federation queue for you may stick — recovery is "wait", not "more restarts." We've burned an afternoon on this.

3.5 Remote join: make_join → send_join

When @bob:hs-a joins !room:hs-b for the first time, hs-a doesn't have the room state yet, so it can't sign a valid m.room.member event by itself.

  1. GET /_matrix/federation/v1/make_join/{roomId}/{userId} to hs-b. hs-b returns an unsigned skeleton of the membership event with the current room state's relevant auth_events filled in, plus the room's room_version.
  2. hs-a fills in the sender, signs it, sends back via PUT /_matrix/federation/v2/send_join/{roomId}/{eventId}.
  3. hs-b validates and replies with the room's full state at the moment of join: state, auth_chain, optionally members_omitted for the lazy-loaded join optimization.

This is where "fast join" (continuwuity calls it that, matrix.org spec calls it "lazy member loading on join", v1.6+) kicks in: hs-a can ask hs-b to omit the full member list, joining quickly with partial state, then backfill later. Continuwuity uses fast-join for federated joins into shared-history rooms; the consequence is that for a brief window after the join, hs-a's view of the room state is incomplete. We've seen this manifest as shortstatehash not found errors on per-event visibility checks. Workaround in shape-rotator-matrix: pin lobby rooms to history_visibility: world_readable, which makes the visibility check a no-op.

4. Continuwuity-specific

Continuwuity is the active fork of conduwuit, which itself was a fork of Conduit. Single-binary Rust homeserver, RocksDB persistence. Aggressively small footprint: ~73MB RAM idle, RocksDB ~62MB after 10 days of light use on a 1.8GB CVM (measured in MATRIX_ONBOARDING.md).

4.1 Schema, defaults

  • RocksDB schema version 18 at time of writing (spring 2026). Schema migrations happen on startup. Migrations are forward-only — there's no documented downgrade path — so test schema bumps in dev before deploying.
  • Default room_version for createRoom is v12. As above, we pin lobbies to v11.
  • No direct_tls build by default. Continuwuity expects to run behind a reverse proxy that terminates TLS; that proxy is what speaks port 8448 to peers. Verified empirically — the federation harness needs an nginx in front of each homeserver to actually do federation over TLS. The cargo features for direct TLS exist but are not the default and are not in the published image. Practical consequence: any federation testing harness needs an nginx (or similar) TLS frontend.

4.2 Registration tokens

The CONDUWUIT_REGISTRATION_TOKEN environment variable is used at first boot only to seed the database. After that, the value is in the DB; changing the env var has no effect. To rotate the registration token you have to either:

  • Use the admin command (!admin server register-token ...) via the admin room, which sets a new token in the DB; or
  • Wipe the data volume and reboot, in which case the env var seeds the fresh DB.

This bites in CI: a harness that rebuilds containers reuses the data volume by default and so stays on the original (often-stale) token, even though the env says otherwise. For our federation-repro harness we run with a fresh per-test data volume to avoid this.

4.3 Admin command surface gaps

Continuwuity 0.5.7's rooms moderation admin command surface, probed via conduwuit --execute "rooms moderation help":

admin rooms moderation:
  ban-room
  ban-list-of-rooms
  unban-room
  list-banned-rooms

What's missing relative to Synapse:

  • No purge_history equivalent. No "delete events older than T" or "delete events up to event ID" admin operation. The only mass-cleanup tool is ban-room, which is functionally a room delete: everyone gets evicted, federation severed, room unrecoverable.
  • No per-event admin delete (Synapse has DELETE /_synapse/admin/v1/rooms/{roomId}/events/{eventId}).
  • No "delete all events from user X" command.

For redaction-based cleanup you fall back to the public client API PUT /rooms/{roomId}/redact/{eventId}/{txnId}, paginating with /messages?dir=b. continuwuity's default rate limit on /redact caps you at ~3.5/s in our measurements even when the admin token bypasses per-user limits — the rate limit on this endpoint appears to be enforced at a different layer. Cleaning up a 600K-event self-DOS this way takes hours; see the May 9 incident retro.

4.4 Admin tokens bypass per-user rate limits

Like Synapse, continuwuity exempts users with the admin role from rc_message per-user rate limits. This is convenient for ops (force-leave, createRoom, reset-password) but turns any buggy send-loop on an admin-tokened bot into a server-saturating flood, since there's no self-throttle. Don't /send as an admin if a non-admin identity would do. Refactor outbound message paths onto a separate non-admin bot identity; reserve the admin token for admin API calls. We're mid-migration on this in shape-rotator-matrix.

4.5 Bot self-heal pattern

shape-rotator-matrix bots check at every boot whether their env-supplied access token still validates against /account/whoami. If not, they re-mint via /login with a password persisted to /data/<bot>_password, and (since PR #37) reuse the same device_id they had before. Reusing the device ID is critical: the crypto store (bot_crypto.db for mautrix-python, matrix-crypto-snapshot.json for matrix-js-sdk) is keyed on (mxid, device_id) and a fresh device ID forces a wipe. Wipe → new uncross-signed device → "Unable to decrypt" wall on every recipient client.

Self-heal works as a recovery mechanism but turns every stale-token deploy into an E2EE migration event. The right operational discipline is "validate the token with whoami before pushing env updates" — easy to forget, and the price of forgetting is high.

5. The bug as worked example

Now we can describe the production incident at every layer above without losing precision.

Scenario. @router-bot on hs-a sends regularly into an encrypted room shared with @user:hs-b. Federation between hs-a and hs-b is healthy under normal load. matrix.org's federation queue for hs-a backs up due to repeated restarts of hs-a (six in five hours, in production); during the backup window, some m.direct_to_device EDUs are dropped (not retried, or aged out of the queue).

Trigger event. The bot's outbound megolm session for the room expires (rotation_period_ms, or membership change, or device add). Bot creates a fresh outbound megolm session — purely local, no network. Bot does the work of §2.2 step 4: build m.room_key, Olm-wrap per recipient device, ship via PUT /sendToDevice. hs-a enqueues for hs-b. hs-a returns 200 to the bot.

The hop that fails. hs-a includes the m.direct_to_device EDU in its next federation transaction to matrix.org's destination server. Either the transaction itself fails and the EDU is in the retry queue, or the transaction succeeds but matrix.org's federation queue for the user's server is backed up and the EDU gets dropped during a queue-purge / restart / capacity-eviction event. Either way: the recipient device never sees the m.room_key.

From matrix-js-sdk's perspective, the call to sendToDevice returned 200. There is no protocol mechanism by which the sender will learn this delivery failed. The outbound session is cached and will be reused for every subsequent message in the room.

The PDU still flows. The bot sends an m.room.encrypted with the actual content (§2.2 step 8). This is a PDU — durable, federated as part of the room DAG, not subject to the same queue dropouts as EDUs. matrix.org's server-server queue will retry this indefinitely until it lands. So the recipient gets the encrypted message but does not have the session to decrypt it.

No automatic recovery. The recipient could in theory send an m.room_key_request (§2.4). matrix-rust-sdk does have this flow, and it would work — but only against devices the recipient has cross-signing trust in. Bots running fresh re-mints (§4.5) are uncross-signed. The request is silently ignored. The room stays broken.

The sender could in theory rotate the megolm session and re-share. But matrix-rust-sdk's default rotation_period_ms is 7 days; nothing in the spec or in the SDK triggers rotation on "I noticed I just had a federation hiccup." matrix-js-sdk doesn't auto-rotate on connection recovery either. So absent operator intervention, the room stays broken indefinitely.

The patch (and why it isn't enough yet). Hermes' Router has an installMegolmAutoRotation path that fires forceDiscardSession on every encrypted room either periodically (default 4h) or on detected sync recovery. The intent is: when federation hiccups, force a fresh session and a fresh m.room_key distribution — which will succeed assuming federation is now healthy. In testing, the patch fires as designed but the harness shows the room still doesn't decrypt after rotation, suggesting the underlying Olm sessions to the recipient devices may also be wedged from the federation window. Open hypothesis. See matrix-megolm-rotation-bug.html for the harness, the current PR status, and the next things to try.
